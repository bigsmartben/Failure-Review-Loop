# 人类可读任务分析报告契约

## 目标

报告以用户业务任务为颗粒度，帮助人类快速理解：

1. 用户想完成什么；
2. Agent 实际如何执行；
3. 双方哪里存在分歧，后来如何对齐；
4. 应优化 Prompt、Skill 还是 Agent。

统计、问题簇和技术证据不能替代任务分析正文。

## 任务边界

- 一个任务对应一个可以独立验收的用户业务目标。
- 用户对同一目标的补充、纠正、确认和返工仍属于原任务。
- `push`、`commit`、`PR`、`merge`、部署、清理分支和更新 Issue 等操作，如果服务于原目标，只是执行过程，不得拆成独立任务。
- 只有用户提出实质不同的新目标时，才建立新任务。

具体示例：用户要求“实现并交付 Issue #8”，后续的实现、测试、推送、合并和更新 Issue 属于同一个任务。

## 正文结构

每个任务固定显示：

- 任务名称；
- 最终结果；
- 用户目标；
- 一至五条关键过程；
- 分歧与对齐。

存在分歧时继续显示：

- 用户期望；
- Agent 实际行为；
- 对齐结果或未解决状态；
- 根因；
- 优化对象；
- 优化方向；
- 验收方式。

没有分歧时明确写“未发现有证据支持的分歧”。

报告最后汇总优化清单。内部任务 ID、分歧 ID、证据 ID、问题簇 ID 和原始对话不进入正文。

## 分歧与对齐

分歧只在用户期望与 Agent 的理解或行为存在直接证据支持的不一致时成立。普通确认、外部操作授权和补充上下文不算分歧。

每条分歧必须同时引用用户与 Agent 消息。已解决分歧必须关联至少一条对齐记录；未解决分歧必须明确标记。

对齐记录说明双方最终确认的内容，以及该确认导致的后续动作。没有分歧也可以记录重要对齐。

## 优化对象

| 对象 | 判断规则 |
|---|---|
| Prompt | 任务规则缺失、含糊或错误 |
| Skill | 技能步骤、任务边界或决策规则导致偏差 |
| Agent | Prompt 和 Skill 已明确，但 Agent 没有遵守 |
| Unknown | 证据不足，无法可靠归因 |

优化方向只描述最小规则修改，不直接修改文件。验收方式必须可重复执行。

## 结构与校验

`findings.schema.json` 定义任务过程、分歧和对齐的数据结构。跨字段校验必须保证：

- 分歧证据属于对应任务，并同时包含用户和 Agent 消息；
- 对齐证据属于对应任务；
- 对齐引用的分歧存在；
- 已解决分歧存在关联对齐；
- 所有用户消息仍被任务覆盖或明确排除。

Python 与 JavaScript 渲染器必须读取共享 fixture，并与同一份 golden Markdown 完全一致。
